# 設定を引き継いでアップデート

`scripts\update.bat` で、GitHubの `Nemesis-Nocturnal-Ray963/effect-site-to-OBS` の **mainブランチの公開ZIP**へ更新できます。通常はGitを使用しません。コピーしたアプリに `.git` が残っていても、Gitの所有者確認やGitHubアカウントの設定は不要です。

## 必要なもの

- Node.js 22.13以降とCorepack（既存の起動スクリプトと同じ実行環境）
- インターネット接続、Windows PowerShell
- アプリのフォルダーへの読み書き権限（Windowsの権限を自動変更することはありません）
- 開発者が `--git` を指定する場合のみGit
- `data`全体と旧プログラムを保存できる空き容量。素材動画やTikTokブラウザプロファイルもバックアップするため、容量・時間に余裕を持って実行してください。

開発者向けの `--git` モードでは `main` にいて、プログラムの変更をコミット済みである必要があります。ローカルの未コミット変更、別ブランチ、更新元と分岐した履歴は上書きせず停止します。通常のダブルクリックは配布先向けで、プログラムをZIP版へ置き換えます。コードを独自に改造している開発用フォルダーでは `--git` を指定してください。

## 通常の手順

1. 配信を終え、アプリのサーバーウィンドウと、アプリから起動したTikTokブラウザを閉じます。更新中は再起動しないでください。
2. アプリのフォルダー内の **`scripts\update.bat`** をダブルクリックします。
3. `Update complete` が表示されたら完了です。
4. **`scripts\start-dev.bat`** から起動し直します。管理画面とOBSのブラウザソースも再読み込みしてください。

更新の有無だけ確認する場合：

```bat
scripts\update.bat --check
```

`--check` はプログラムの置き換え、依存関係のインストール、データのバックアップを行いません。公開GitHub APIで更新情報を確認し、作業用のロックファイルを一時作成します。開発者用の `--git --check` では `git fetch` を使います。

### 旧版で「detected dubious ownership」が出た場合

配布元と実行者のWindowsユーザーが異なるため、旧版が自動選択したGit更新が止まっています。設定データの破損を意味するものではありません。

修正版の `scripts/update.bat` と `scripts/update.mjs` を既存アプリの `scripts` フォルダーへ上書きしてください。その後は `update.bat` のダブルクリックで公開ZIPから更新できます。Gitの `safe.directory` 設定は変更しません。

配布先にはアプリ全体とこの2ファイルが必要です。bat単体だけでは動作しません。公開リポジトリへ接続できること、Node.js・Corepackがあること、配布先フォルダーに書き込めることが前提です。

## 引き継ぐ内容

アプリ直下の **`data` を置き換えません**。以下をまとめてバックアップしたうえで、元のファイルを引き続き使用します。

- エフェクト設定、プリセット、ゲーム用プリセット
- Overlay設定
- 画像・動画・音声素材、素材カタログ
- ギフトカタログ、イベント・タイマートリガーのSQLiteデータベース
- APIキー、TikTokブラウザプロファイル
- アプリ直下の `.env` と `.env.*`

画面上に落下・蓄積している物体など、メモリだけに保存される状態は再起動で消えます。

今回は保存形式を変更せず、ファイルをそのまま引き継ぐ仕組みです。将来、設定やデータベースの形式を変更する機能を追加するときは、そのバージョン側で旧形式からの移行処理を実装する必要があります。

## ZIP版について

通常更新にはGitをインストールする必要はありません。GitHubから最新コミットのソースZIPを取得し、アプリのプログラム部分を更新してビルドします。既存の `.git` はそのまま残しますが、Gitの履歴は更新しません。次回も通常のZIP更新を使えます。

古いZIPに更新スクリプトが含まれていない場合は、この仕組みを含む新しいバージョンから、次の2ファイルを既存アプリの `scripts` フォルダーへコピーしてから実行してください。

- `update.bat`
- `update.mjs`

最新版を別フォルダーへ展開して起動する操作とは異なり、**いつも使用しているアプリのフォルダーで実行**します。既存の `data` を新しい空の `data` で置き換えないでください。

ZIP版の `apps`、`packages`、`scripts`、`docs` と配布設定ファイルは、配布されたプログラムへ置き換えます。これらの中に独自改造や手作業で置いた素材がある場合は、更新前に別途保存してください。Git版のような変更検出はできません。旧プログラム自体はバックアップに残します。

更新先にこのアップデーターが含まれていない場合や、ZIPに `data` などの保護対象が混入している場合は、置き換え前に停止します。

## バックアップと失敗時の動作

バックアップ先はアプリ内の **`.updates\日時-コミットID\`** です。実行時にもフルパスを表示します。

| 保存先 | 内容 |
| --- | --- |
| `update.json` | 更新前後のコミット、処理状態、移動済みファイル一覧、失敗理由 |
| `data` | 更新直前の設定・素材・データベース・ブラウザプロファイル |
| `environment` | 更新直前の `.env` 類 |
| `previous-code.zip` | Git版の更新前コード |
| `previous` | ZIP版の更新前プログラム |
| `previous-artifacts` | 更新前の依存関係とビルド済みファイル |
| `failed` | 復旧時に退避した、更新失敗したプログラムやビルド |

依存関係の取得・ビルドで失敗した場合は、旧コードと退避していた依存関係・ビルドを戻します。ネットワーク障害時でも、旧依存関係の再ダウンロードを必要としない復旧です。`data` は自動で巻き戻しません。

バックアップにはAPIキーやブラウザのログイン情報が含まれます。公開用ZIPやGitへ追加しないでください。`.updates` はGit管理対象から除外しています。正常動作を確認した古いバックアップは、必要に応じてエクスプローラーから削除できます。

### 強制終了・停電・復旧失敗

処理途中でWindowsや更新ウィンドウを強制終了すると、自動復旧は実行できません。`.updates\update.lock` が残るため、次の更新は停止します。

1. アプリと更新処理が動いていないことを確認し、アプリを起動せず最新バックアップの `update.json` を確認します。
2. `complete` なら更新済み、`rolled-back` なら旧版へ復旧済みです。この場合だけ、残った `update.lock` を削除して再試行できます。
3. `backing-up` ではプログラムの変更前です。バックアップ中に停止したことを確認してからロックを削除して再実行します。
4. `updating` または `recovery-required` の場合は、ロックを消して再実行せず、バックアップを保持して復旧を依頼してください。`previous` と `previous-artifacts` が部分的に退避された状態の可能性があります。

自動復旧に失敗した場合は `.updates\recovery-required.json` も作成し、後続の更新を止めます。復旧が完了したことを確認してから、このマーカーとロックを取り除いてください。

GitHubの最新版がまだ配布されていない段階では更新できません。開発側で変更をGitHubへプッシュしてから配布・更新を行います。
